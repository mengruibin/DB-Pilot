## 1. LLM 生成的 SQL 缺少性能优化处理

**日期**: 2026-07-05

### 问题描述

大模型如果输出了未做优化的 SQL（例如使用了未加索引的查询列导致全表扫描），项目中没有做任何性能层面的处理或优化。

经过对 SQL 执行全链路分析发现：

```
LLM 生成 SQL → SafeToolNode → 安全审计(sqlglot) → 直接执行 → 返回结果
                                   ↑
                          仅检查 DROP/ALTER/TRUNCATE
                          零性能分析
```

安全审计器 (`sql_auditor.py`) 仅检查 DDL/DML 等危险操作，完全不涉及性能分析。项目虽已有 `explain_query` 工具、EXPLAIN 诊断引擎（LLM + 规则引擎双通道）、慢查询监控等能力，但都是被动等待 LLM 自主调用的，没有集成到执行流程中。

### 解决方案

采用**三层渐进式防护**体系：

#### Layer 1: Prompt 增强（零开销）

- **`app/prompts/nl2sql.py`**: NL2SQL 系统提示新增 6 条「性能优化规则」：
  - 优先使用有索引的列作为 WHERE/JOIN 条件
  - 避免 `SELECT *`，明确列出需要的列
  - 大表查询添加合理 LIMIT
  - 避免在 WHERE 中对列使用函数（如 `YEAR(col)`）
  - 避免前置通配符 `LIKE '%keyword'`
  - 多表 JOIN 时小表驱动大表

- **`app/agent/graph.py`**: `_build_system_prompt()` 工作原则增加：
  - 执行 SQL 前必须用 `describe_table` 了解索引信息
  - 复杂查询考虑使用 `explain_query` 检查执行计划
  - 发现全表扫描/文件排序/临时表等问题应改写 SQL

#### Layer 2: NL2SQL 自动性能审计（~10ms）

- **`app/engine/nl2sql.py`**: 新增 `_performance_audit_sql()` 函数
  - LLM 生成 SQL 后自动执行 EXPLAIN
  - 通过规则引擎分析 EXPLAIN 输出（无 LLM 调用，即时分析）
  - 检测全表扫描、文件排序、临时表等问题
  - 非阻断性——异常静默捕获，绝不阻塞查询执行
  - `generate_sql()` 新增可选 `adapter` 参数

#### Layer 3: Agent 性能检查护栏（<1ms）[已移除]

- **`app/agent/safety.py`**: 曾新增 `PerformanceCheck` 安全护栏（已在后续迭代中移除，由 RowEstimationCheck 完全接管）

- **`app/agent/tool_node.py`**: 安全护栏的 `warnings` 前缀到 `ToolMessage`（已移除 PerformanceCheck，仅保留 RowEstimationCheck 的阻断/放行）

#### 修复: BOTTLENECK_PATTERNS 匹配 JSON EXPLAIN 格式

- **`app/prompts/diagnosis.py`**: `BOTTLENECK_PATTERNS` 关键字列表增加 JSON 格式匹配：
  - `"access_type": "ALL"` → 全表扫描
  - `"using_filesort": true` → 文件排序
  - `"using_temporary_table": true` → 临时表
  - `Seq Scan` → PostgreSQL 全表扫描

### 修改文件

| 文件 | 修改类型 |
|------|----------|
| `backend/app/prompts/diagnosis.py` | 修复: JSON EXPLAIN 关键字匹配 |
| `backend/app/prompts/nl2sql.py` | 增强: 系统提示增加性能优化规则 |
| `backend/app/agent/graph.py` | 增强: Agent 工作原则增加性能指引 |
| `backend/app/engine/nl2sql.py` | 新增: `_performance_audit_sql()` + `generate_sql()` 适配器参数 |

## 2. LLM 生成错误 SQL 时缺少结构化错误反馈

**日期**: 2026-07-06

### 问题描述

当 LLM 生成了错误的 SQL（表名不存在、字段名拼写错误等），项目中对错误的处理是"事后补救"模式，完全依赖数据库原生报错：

```
LLM 生成 SQL → 执行 → 数据库报错（如 1146 Table 'x' doesn't exist）
  → 适配器包装为 ValueError("SQL 执行错误：(1146, ...)")
  → run_query 返回 {"error": "run_query 执行失败", "detail": "ValueError: ..."}
  → tool_node 包装为 ToolMessage("工具执行失败: ValueError: ...")
```

LLM 收到的是一段**非结构化的、被截断的**错误文本，存在以下问题：

1. 数据库原生错误码（如 MySQL `1146`、`1054`）对 LLM 不够友好
2. 错误信息中缺少纠错指导——LLM 不知道应该调用 `list_tables` 还是 `describe_table`
3. 错误文本在多层包装中逐级丢失信息（被截断到 200 字符）
4. 三种数据库（MySQL/PostgreSQL/Oracle）错误格式各异，LLM 难以统一理解

### 解决方案

新增 **SQL 错误解析引擎**，在 `run_query` 工具内部的 `except` 分支中，将数据库原生错误转换为结构化、带纠错指导的 `ParsedError`：

```
run_query(sql)
  ├── SQL 安全审计（不变）
  ├── 连接 + 执行 SQL
  │     ├── 成功 → 脱敏 → 返回结果（不变）
  │     └── 失败 → except
  │           ├── parse_db_error(exc, db_type, sql)  ← 新增
  │           └── 返回结构化错误 dict                ← 新增
  └── tool_node 将 dict 序列化为 JSON → ToolMessage → LLM 自我纠正
```

#### 错误解析引擎：`app/engine/sql_error_parser.py`

识别 4 种错误类型：

| ErrorType | 含义 | 纠错指引 |
|-----------|------|----------|
| `TABLE_NOT_FOUND` | 表不存在 | 请使用 list_tables 查看所有可用的表名 |
| `COLUMN_NOT_FOUND` | 字段不存在 | 请使用 describe_table 查看表的完整字段列表 |
| `SYNTAX_ERROR` | SQL 语法错误 | 请检查 SQL 语法是否正确 |
| `PERMISSION_DENIED` | 权限不足 | 请联系管理员授予相应权限 |
| `UNKNOWN` | 未识别错误 | 保留原始信息 + 通用兜底建议 |

**三大数据库错误码覆盖**：

| 数据库 | 表不存在 | 字段不存在 | 语法错误 | 权限不足 |
|--------|----------|------------|----------|----------|
| MySQL | `1146` | `1054` | `1064` | `1142` |
| PostgreSQL | `relation "X" does not exist` | `column "X" does not exist` | `syntax error at or near` | `permission denied for` |
| Oracle | `ORA-00942` | `ORA-00904` | `ORA-00900` | `ORA-01031` |

实现方式：纯正则匹配，零新依赖。从异常消息中提取具体的表名/字段名，构造中文纠错描述。

#### 结构化错误返回值

**之前**（`_safe_tool_call` 通用包装）：
```json
{
  "error": "run_query 执行失败",
  "detail": "ValueError: SQL执行错误：(1146, \"Table 'test.nonexistent' doesn't exist\")"
}
```

**之后**（解析器输出）：
```json
{
  "error": "SQL 执行失败：表 'nonexistent' 在当前数据库中不存在",
  "error_type": "TABLE_NOT_FOUND",
  "detail": "表 'nonexistent' 在当前数据库中不存在",
  "suggestion": "请使用 list_tables 查看所有可用的表名，然后用 describe_table 确认表结构",
  "sql": "SELECT * FROM nonexistent WHERE id = 1",
  "audit_status": "execution_error"
}
```

LLM 从 ToolMessage（JSON 字符串）中可直接读取 `error_type`、`suggestion` 等字段，精准定位问题并调用正确工具修正。

#### 关键设计决策

- **放在工具内部而非安全护栏**：安全护栏（`safety.py`）在适配器连接之前执行，无法复用数据库连接。工具内部已有连接逻辑，错误解析不增加额外开销
- **不修改 tool_node.py**：`run_query` 的 except 现在返回结构化 dict 而非抛异常，ToolMessage 走正常 `_json.dumps(result)` 路径（第 183 行），不会被截断
- **不修改 AgentState**：纯工具层面的改动，零状态

| 文件 | 修改类型 |
|------|----------|
| `backend/app/engine/sql_error_parser.py` | **新增** — 数据库错误解析引擎（150 行） |
| `backend/app/agent/tools/query.py` | 修改 — `run_query` 的 except 分支使用解析器 |
| `backend/tests/test_sql_error_parser.py` | **新增** — 22 个单元测试 |

- 60/60 已有测试不受影响

## 3. user_role 旧默认值为 standard，应用层缺少权限判定

**日期**: 2026-07-06

### 问题描述

`user_role` 在 `chat.py` 和 `troubleshoot.py` 中原本以 `"standard"` 作为默认兜底，admin 角色分支是死代码。同时 INSERT 语句在 SQL 审计中未被列入 `_ADMIN_ONLY_STATEMENTS`，应用层没有拦截——实际依赖 MySQL 适配器层的 `SET SESSION TRANSACTION READ ONLY`（ERROR 1792）兜底，属于"偶然防御"。

```
INSERT 穿越轨迹（改动前）:
  SQLAuditCheck(_FORBIDDEN_STATEMENTS 没有 INSERT) → 放行 ✅
  SQLAuditCheck(_ADMIN_ONLY_STATEMENTS 没有 INSERT) → 放行 ✅
  ReadOnlyCheck(预留桩) → 放行 ✅  （注：ReadOnlyCheck 已于 2026-07-08 移除）
  PerformanceCheck(非 SELECT 跳过) → 放行 ✅  （注：PerformanceCheck 已于后续迭代中移除）
  run_query 内部 audit() → 放行 ✅
  adapter.execute("INSERT INTO ...") → MySQL ERROR 1792 拦截 🔥
```

三层审计（安全护栏链 ×2 + 工具内部）全部放行，全靠 MySQL 会话级只读事务兜底。如果适配器未设置 READ ONLY（如未来扩展的 admin 连接），INSERT 将直接写入数据库。

### 解决方案

采用**数据库权限映射**模式——DB-Pilot 不自创权限体系，权限源头来自目标数据库用户的 GRANT：

#### 1. GRANT 解析引擎：`app/engine/grant_detector.py`（新建）

连接 MySQL 执行 `SHOW GRANTS FOR CURRENT_USER()`，解析 GRANT 语句自动判定角色：

| 解析到的权限 | user_role | 效果 |
|-------------|-----------|------|
| 仅有 SELECT | `"readonly"` | INSERT/UPDATE/DELETE 在 SQL 审计层拦截 |
| 有 INSERT/UPDATE/DELETE | `"admin"` | 跳过 READ ONLY 事务，写操作放行 |
| ALL PRIVILEGES | `"admin"` | 同上 |
| 连接失败/异常 | `"readonly"` | 安全降级，宁可误拦不可漏放 |

**缓存**：内存 TTL 缓存（5 分钟，惰性过期），重启后重新检测。DBA 改 GRANT 后最多 5 分钟生效。

#### 2. 安全审计补齐（`app/engine/sql_auditor.py`）

`_ADMIN_ONLY_STATEMENTS` 增加 INSERT，与 DELETE/UPDATE 同级管控：

```python
_ADMIN_ONLY_STATEMENTS = {
    "DELETE": "DELETE 操作需要 admin 权限",
    "UPDATE": "UPDATE 操作需要 admin 权限",
    "INSERT": "INSERT 操作需要 admin 权限",   # 补齐缺口
}
```

#### 3. 适配器按角色控制只读事务

`BaseAdapter.connect()` 签名增加 `user_role` 参数：

- MySQL：admin 跳过 `SET SESSION TRANSACTION READ ONLY`
- PostgreSQL/Oracle：签名同步（功能暂不变）

#### 4. 角色预检注入 + 缓存共享

`_resolve_connection_config()`（chat.py/troubleshoot.py）中预检角色，写入 `conn_config["user_role"]`，并将默认兜底从 `"standard"` 调整为更保守的 `"readonly"`。`_role_cache` 在 `grant_detector` 模块级别共享。

#### 5. test_connection 同步检测

测试连接时顺带做 SHOW GRANTS 并缓存，后续 SSE 聊天直接命中。

#### 6. 全链路可观测

| 日志点 | 级别 | 说明 |
|--------|------|------|
| `角色缓存命中` | debug | 缓存命中时记录 role |
| `角色缓存未命中` | debug | 无缓存或已过期 |
| `角色缓存已过期` | info | 惰性过期时记录旧 role |
| `角色缓存已更新` | info | 写入缓存时记录 role + TTL |
| `角色来自实时检测` | info | 未命中时 detect 的结果 |
| `MySQL 权限检测完成` | info | SHOW GRANTS 返回的行数 |
| `用户角色判定结果` | info | 解析后的角色值 |
| `连接配置已解析` | info | conn_config 中最终 user_role |

所有日志带 `role_<hex>` 追踪 ID，可关联到具体请求。

### 数据流总览

```
POST /api/connections/{id}/test         ← 测试连接时预检
  → detect_mysql_role() → SHOW GRANTS
  → _role_cache[conn_id] = "admin"
  → adapter.connect(user_role="admin")

POST /api/chat/stream                   ← SSE 聊天时命中缓存
  → _resolve_connection_config()
    → get_cached_role("conn_id") → "admin" ← 命中缓存，无额外连接
    → conn_config["user_role"] = "admin"
  → safe_tools_node
    → SQLAuditCheck(user_role=admin)
      → INSERT: user_role="admin" 放行 ✅
      → DELETE: user_role="admin" 放行 ✅
    → run_query(user_role=admin)
      → adapter.connect(config, user_role="admin")
        → 跳过 READ ONLY
      → adapter.execute("INSERT INTO ...")
        → 执行成功 ✅
```

## 4. EXPLAIN 多维度安全评估 — 大表查询执行前阻断 + LLM 上下文保护

**日期**: 2026-07-18

### 问题描述

DB-Pilot 对 SQL 执行没有任何行数/资源限制，存在三重风险：

1. **数据库层面**：大表全表扫描消耗大量 IO/CPU/内存，可能影响其他业务
2. **应用层面**：全量结果集加载到内存，可能导致 OOM
3. **LLM 层面**：百万行 JSON 序列化后塞入 ToolMessage，上下文窗口溢出导致 LLM 调用失败

曾有的 `PerformanceCheck` 仅做静态文本分析（正则匹配 `SELECT *`、缺少 `LIMIT`），无法感知真实数据量，也不能阻断执行（已移除）。

### 解决方案

设计 **四阶段防护体系**，在 SQL 执行前通过 EXPLAIN 获取多维度指标并用规则引擎评估：

```
execute_sql 被 LLM 调用
 │
 ├─ Phase 1: [已移除] PerformanceCheck（静态文本分析，无阻断效果，已移除）
 │
 ├─ Phase 2: RowEstimationCheck（一次 EXPLAIN 往返，约 10-50ms）
 │   ├─ adapter.explain(sql) → 获取原始 EXPLAIN
 │   ├─ extract_metrics() → 5 维标准化指标
 │   ├─ evaluate() → 规则引擎（6 条 CRITICAL 规则，WARNING 已移除）
 │   └─ EXPLAIN 失败 → 降级放行（不阻断正常业务）
 │
 ├─ Phase 3: 实际执行
 │
 └─ Phase 4: LLM 上下文保护（结果后处理）
     └─ truncate_result_for_llm() → 截断超量行数/字符数
```

#### ExplainMetrics — 跨数据库统一评估指标

| 维度 | 指标 | MySQL | PostgreSQL | Oracle |
|------|------|-------|-----------|--------|
| D1: 访问方式 | `access_pattern` | `access_type` → 分类 | `Node Type` → 分类 | `Operation` → 分类 |
| D2: 数据规模 | `estimated_rows_examined` | `rows_examined_per_scan` / `rows` | `Plan Rows` | `Rows` 列 |
| D2: 数据规模 | `estimated_rows_output` | `rows_produced_per_join` | `Plan Rows` | `Rows` 列（Id=0） |
| D2: 数据规模 | `row_width_bytes` | `used_columns` × 50 | `Plan Width` | `Bytes ÷ Rows` |
| D3: 成本 | `query_cost` | `cost_info.query_cost` | `Total Cost` | `Cost` 列 |
| D4: 额外操作 | `extra_operations` | `using_filesort` / `using_temporary_table` | Sort/Hash/Materialize 节点 | Operation 含 SORT/HASH/TEMP |

#### 硬编码阈值常量

所有阈值在 `explain_estimator.py` 中作为代码常量管理，修改需 Code Review，不依赖 .env 配置：

| 阈值 | 值 | 作用 |
|------|-----|------|
| `_FULL_SCAN_BLOCK_ROWS` | 5,000 | 全表扫描阻断线 |
| `_FULL_SCAN_WARN_ROWS` | 500 | 全表扫描警告线 |
| `_INDEX_SCAN_BLOCK_ROWS` | 100,000 | 索引扫描阻断线 |
| `_INDEX_SCAN_WARN_ROWS` | 10,000 | 索引扫描警告线 |
| `_INDEX_LOOKUP_BLOCK_ROWS` | 500,000 | 索引查找警告线 |
| `_RESULT_BLOCK_ROWS` | 10,000 | 结果行数阻断线（保护 LLM 上下文） |
| `_RESULT_WARN_ROWS` | 500 | 结果行数警告线 |
| `_RESULT_BLOCK_BYTES` | 500,000 (≈500KB) | 结果字节数阻断线 |
| `_MAX_LLM_RESULT_ROWS` | 200 | 返回 LLM 的最大行数（阶段 4 截断） |
| `_MAX_LLM_RESULT_CHARS` | 80,000 | 返回 LLM 的最大字符数（阶段 4 截断） |

#### 规则引擎（按优先级从高到低）

6 条 CRITICAL 规则（阻断执行）：

| 规则 | 条件 | 说明 |
|------|------|------|
| R1 | FULL_SCAN + rows > 5,000 | 全表扫描大行数 |
| R2 | FULL_SCAN + cost > 1,000 | 全表扫描高成本 |
| R3 | 非 INDEX_LOOKUP/CONST + rows > 100,000 | 超大扫描行数兜底 |
| R4 | rows_output > 10,000 | 结果集过大（LLM 上下文保护） |
| R5 | rows_output × row_width > 500KB | 结果字节数过大 |
| R6 | temporary + rows > 50,000 | 临时表大数据量 |

5 条 WARNING 规则（仅告警，已移除）：

| 规则 | 条件 | 说明 |
|------|------|------|
| W1 | FULL_SCAN + rows > 500 | 全表扫描中等行数 |
| W2 | INDEX_SCAN + rows > 10,000 | 索引扫描较多行数 |
| W3 | rows_output > 500 | 结果行数偏多 |
| W4 | filesort + rows > 5,000 | 文件排序+较大数据 |
| W5 | INDEX_LOOKUP + rows > 500,000 | 索引查找极大行数 |

#### 关键设计决策

- **硬编码阈值**：不在 .env 配置，避免运维误配。所有阈值作为代码常量，修改需 Code Review

## 5. 工具优化：锁排查、慢查询、健康巡检全方位增强

**日期**: 2026-07-23

### 问题描述

基于一次完整的数据库问题排查过程（慢查询分析 → 锁等待排查 → 锁详情查询 → KILL 事务），让Agent自检、提出工具优化建议，发现现有工具存在以下问题：

1. **check_locks 信息严重不足**：只返回事务 ID 和等待状态，缺少锁定的表名、行键值、锁模式（S/X/GAP/Next-key），无法区分"持有锁"和"等待锁"
2. **get_slow_queries 形参实参不匹配**：`time_range` 参数接受 "6h"/"24h"/"7d"，但 MySQL 适配器硬编码为 `INTERVAL 1 HOUR`，所有时间范围实际效果相同；慢查询日志未开启时返回空列表，用户无法区分"没有慢查询"还是"日志没开"
3. **execute_sql 系统表查询报错**：查询 `INNODB_SYS_TABLES`、`performance_schema.data_locks` 等系统表时报错，且无数据库版本感知，MariaDB 的系统表差异导致查询失败
4. **run_health_check 建议空泛**：缓冲池命中率仅 32.62% 时建议只说"增加 innodb_buffer_pool_size"，没有给出当前值和建议值；检查项之间缺乏关联分析
5. **锁详情查询缺失**：没有专用工具查询特定事务的锁记录和锁类型，需 5+ 次手动解析 SHOW ENGINE INNODB STATUS
6. **KILL 操作无标准化工具**：需通过 execute_sql 执行 KILL，可能被安全策略拦截，且无确认机制和风险提示
7. **EXPLAIN 方法存在 SQL 注入风险**：适配器层 explain() 方法使用裸 f-string 拼接用户 SQL，无任何预检

**排查数据**：15+ 次工具调用中，4 次查询失败、5+ 次因信息不足需重复查询。

### 解决方案

#### 方案设计

输出优化方案文档 `docs/tool-optimization-plan.md`，7 项改进按 P0→P3 优先级分 5 批次实施：

| 批次 | 任务 | 优先级 | 说明 |
|------|------|--------|------|
| 1 | 修复 EXPLAIN 方法 SQL 注入 + 增加版本检测 | P0 | 基础设施修复 |
| 2 | check_locks 增强 + get_slow_queries 增强 | P0 | 核心功能增强 |
| 3 | 新增 analyze_locks + explain_query 联动 | P1 | 新增功能 |
| 4 | run_health_check 增强 + 新增 kill_transaction | P2 | 能力增强 |
| 5 | explain_query 与慢查询自动联动 | P3 | 锦上添花 |

#### 执行过程

##### 批次 1：基础设施修复

**1.1 EXPLAIN f-string 安全修复**（`backend/app/db/mysql.py`、`postgresql.py`、`oracle.py`）

三个适配器的 `explain()` 方法使用裸 f-string 拼接用户 SQL。虽然上游有 `SQLAuditCheck`，但适配器层作为底层能力应有第二道防线。

修复方式：三个适配器分别增加多语句检测（`;` 分隔符检测）和单引号转义。EXPLAIN 不支持参数化占位符，因此安全拼接 + 预检是正确做法。

**1.2 MySQL/MariaDB 版本检测**（`backend/app/db/mysql.py`）

在 `MySQLAdapter.connect()` 中连接建立后执行 `SELECT VERSION(), @@version_comment`，检测是 MySQL 还是 MariaDB，解析版本号三元组。存储为 `self._db_vendor` 和 `self._version_int`，新增 `is_mariadb()` 和 `get_db_version()` 方法。

同步更新 `AdapterCapabilities`（`base.py`），新增 `supports_lock_analysis` 和 `supports_kill_transaction` 两个能力字段。

##### 批次 2：核心功能增强

**2.1 check_locks 返回完整锁拓扑**（`backend/app/db/mysql.py`、`troubleshoot.py`）

MySQL `get_lock_info()` 重写为版本感知路由：
- MySQL 8.0+：联表查询 `performance_schema.data_locks` + `data_lock_waits` + `PROCESSLIST`，精确区分 held_locks/waiting_locks
- MySQL 5.7/MariaDB：增强 `SHOW ENGINE INNODB STATUS` 解析

返回结构从 `list[dict]` 改为 `{held_locks, waiting_locks, total_held, total_waiting, summary}`，每个锁记录包含 `table_name`、`lock_mode`（Record/Gap/Next-key）、`lock_type`（S/X）。

### 发现的 Bug 与修复

#### Bug 1：参数占位符格式不兼容

**现象**：`analyze_locks` 报 `performance_schema.data_locks 不可访问`

**根因**：`_analyze_mysql_locks` 和 `kill_transaction` 中 SQL 使用了 `%(name)s` 命名占位符，但 MySQL 适配器的 `execute()` 方法通过 `list(params.values())` 转为位置参数后传给 `cur.execute(sql, list)`，命名占位符不匹配。

修复范围：

| 位置 | 原写法 | 修复后 |
|------|--------|--------|
| `_analyze_mysql_locks` | `%(transaction_id)s` | `%s` |
| `kill_transaction` MySQL | `%(tid)s` | `%s` |
| `_analyze_pg_locks` | `%(pid)s` | `$1` |
| `kill_transaction` PostgreSQL | `%(pid)s` | `$1` |

#### Bug 2：supports_lock_analysis 版本阈值误判

**现象**：MySQL 5.7 被误判为"不支持细粒度锁分析"

**根因**：`performance_schema.data_locks` 表在 MySQL 8.0 才引入。MySQL 5.7 有 `INFORMATION_SCHEMA.INNODB_LOCKS` 和 `INNODB_LOCK_WAITS` 可替代。修复后添加了 5.7 的独立查询路径。

### 设计缺陷发现

**confirm_node 仅拦截 SQL 写操作**：当前实现假设所有危险操作都是通过 execute_sql 执行的写 SQL。对于 kill_transaction 等无 sql 参数的危险工具，即使声明 `needs_write_confirmation=True`，也不会被 confirm_node 拦截触发用户确认流程。后续需改造 confirm_node 以兼容非 SQL 类的危险操作确认。
