## 1. LLM 生成的 SQL 缺少性能优化处理

**日期**: 2026-07-05

### 问题描述

大模型如果输出了未做优化的 SQL（例如使用了未加索引的查询列导致全表扫描），项目中没有做任何性能层面的处理或优化。

经过对 SQL 执行全链路分析发现：

```
LLM 生成 SQL → SafeToolNode → 安全审计(sqlglot) → 直接执行 → 返回结果
                                   ↑
                          仅检查 DROP/ALTER/TRUNCATE
                          零性能分析
```

安全审计器 (`sql_auditor.py`) 仅检查 DDL/DML 等危险操作，完全不涉及性能分析。项目虽已有 `explain_query` 工具、EXPLAIN 诊断引擎（LLM + 规则引擎双通道）、慢查询监控等能力，但都是被动等待 LLM 自主调用的，没有集成到执行流程中。

### 解决方案

采用**三层渐进式防护**体系：

#### Layer 1: Prompt 增强（零开销）

- **`app/prompts/nl2sql.py`**: NL2SQL 系统提示新增 6 条「性能优化规则」：
  - 优先使用有索引的列作为 WHERE/JOIN 条件
  - 避免 `SELECT *`，明确列出需要的列
  - 大表查询添加合理 LIMIT
  - 避免在 WHERE 中对列使用函数（如 `YEAR(col)`）
  - 避免前置通配符 `LIKE '%keyword'`
  - 多表 JOIN 时小表驱动大表

- **`app/agent/graph.py`**: `_build_system_prompt()` 工作原则增加：
  - 执行 SQL 前必须用 `describe_table` 了解索引信息
  - 复杂查询考虑使用 `explain_query` 检查执行计划
  - 发现全表扫描/文件排序/临时表等问题应改写 SQL

#### Layer 2: NL2SQL 自动性能审计（~10ms）

- **`app/engine/nl2sql.py`**: 新增 `_performance_audit_sql()` 函数
  - LLM 生成 SQL 后自动执行 EXPLAIN
  - 通过规则引擎分析 EXPLAIN 输出（无 LLM 调用，即时分析）
  - 检测全表扫描、文件排序、临时表等问题
  - 非阻断性——异常静默捕获，绝不阻塞查询执行
  - `generate_sql()` 新增可选 `adapter` 参数

#### Layer 3: Agent 性能检查护栏（<1ms）

- **`app/agent/safety.py`**: 新增 `PerformanceCheck` 安全护栏
  - 纯静态分析，无需数据库连接
  - 检测 3 种反模式：`SELECT *`、缺少 LIMIT、WHERE 列上使用函数
  - 始终返回 `blocked=False`，仅通过 `warnings` 提供性能提示
  - 注册到默认护栏链（`SQLAuditCheck → ReadOnlyCheck → PerformanceCheck`）

- **`app/agent/tool_node.py`**: 安全护栏的 `warnings` 前缀到 `ToolMessage`
  - Agent 收到 `[性能提示] ...` 前缀后，可自主决定调用 `explain_query` 或改写 SQL

#### 修复: BOTTLENECK_PATTERNS 匹配 JSON EXPLAIN 格式

- **`app/prompts/diagnosis.py`**: `BOTTLENECK_PATTERNS` 关键字列表增加 JSON 格式匹配：
  - `"access_type": "ALL"` → 全表扫描
  - `"using_filesort": true` → 文件排序
  - `"using_temporary_table": true` → 临时表
  - `Seq Scan` → PostgreSQL 全表扫描

### 修改文件

| 文件 | 修改类型 |
|------|----------|
| `backend/app/prompts/diagnosis.py` | 修复: JSON EXPLAIN 关键字匹配 |
| `backend/app/prompts/nl2sql.py` | 增强: 系统提示增加性能优化规则 |
| `backend/app/agent/graph.py` | 增强: Agent 工作原则增加性能指引 |
| `backend/app/engine/nl2sql.py` | 新增: `_performance_audit_sql()` + `generate_sql()` 适配器参数 |
| `backend/app/agent/safety.py` | 新增: `PerformanceCheck` 类 + 静态分析辅助函数 |
| `backend/app/agent/tool_node.py` | 增强: 安全护栏警告传递到 Agent |

- JSON EXPLAIN 关键字匹配验证通过
- Agent 系统提示已包含性能相关指引

## 2. LLM 生成错误 SQL 时缺少结构化错误反馈

**日期**: 2026-07-06

### 问题描述

当 LLM 生成了错误的 SQL（表名不存在、字段名拼写错误等），项目中对错误的处理是"事后补救"模式，完全依赖数据库原生报错：

```
LLM 生成 SQL → 执行 → 数据库报错（如 1146 Table 'x' doesn't exist）
  → 适配器包装为 ValueError("SQL 执行错误：(1146, ...)")
  → run_query 返回 {"error": "run_query 执行失败", "detail": "ValueError: ..."}
  → tool_node 包装为 ToolMessage("工具执行失败: ValueError: ...")
```

LLM 收到的是一段**非结构化的、被截断的**错误文本，存在以下问题：

1. 数据库原生错误码（如 MySQL `1146`、`1054`）对 LLM 不够友好
2. 错误信息中缺少纠错指导——LLM 不知道应该调用 `list_tables` 还是 `describe_table`
3. 错误文本在多层包装中逐级丢失信息（被截断到 200 字符）
4. 三种数据库（MySQL/PostgreSQL/Oracle）错误格式各异，LLM 难以统一理解

### 解决方案

新增 **SQL 错误解析引擎**，在 `run_query` 工具内部的 `except` 分支中，将数据库原生错误转换为结构化、带纠错指导的 `ParsedError`：

```
run_query(sql)
  ├── SQL 安全审计（不变）
  ├── 连接 + 执行 SQL
  │     ├── 成功 → 脱敏 → 返回结果（不变）
  │     └── 失败 → except
  │           ├── parse_db_error(exc, db_type, sql)  ← 新增
  │           └── 返回结构化错误 dict                ← 新增
  └── tool_node 将 dict 序列化为 JSON → ToolMessage → LLM 自我纠正
```

#### 错误解析引擎：`app/engine/sql_error_parser.py`

识别 4 种错误类型：

| ErrorType | 含义 | 纠错指引 |
|-----------|------|----------|
| `TABLE_NOT_FOUND` | 表不存在 | 请使用 list_tables 查看所有可用的表名 |
| `COLUMN_NOT_FOUND` | 字段不存在 | 请使用 describe_table 查看表的完整字段列表 |
| `SYNTAX_ERROR` | SQL 语法错误 | 请检查 SQL 语法是否正确 |
| `PERMISSION_DENIED` | 权限不足 | 请联系管理员授予相应权限 |
| `UNKNOWN` | 未识别错误 | 保留原始信息 + 通用兜底建议 |

**三大数据库错误码覆盖**：

| 数据库 | 表不存在 | 字段不存在 | 语法错误 | 权限不足 |
|--------|----------|------------|----------|----------|
| MySQL | `1146` | `1054` | `1064` | `1142` |
| PostgreSQL | `relation "X" does not exist` | `column "X" does not exist` | `syntax error at or near` | `permission denied for` |
| Oracle | `ORA-00942` | `ORA-00904` | `ORA-00900` | `ORA-01031` |

实现方式：纯正则匹配，零新依赖。从异常消息中提取具体的表名/字段名，构造中文纠错描述。

#### 结构化错误返回值

**之前**（`_safe_tool_call` 通用包装）：
```json
{
  "error": "run_query 执行失败",
  "detail": "ValueError: SQL执行错误：(1146, \"Table 'test.nonexistent' doesn't exist\")"
}
```

**之后**（解析器输出）：
```json
{
  "error": "SQL 执行失败：表 'nonexistent' 在当前数据库中不存在",
  "error_type": "TABLE_NOT_FOUND",
  "detail": "表 'nonexistent' 在当前数据库中不存在",
  "suggestion": "请使用 list_tables 查看所有可用的表名，然后用 describe_table 确认表结构",
  "sql": "SELECT * FROM nonexistent WHERE id = 1",
  "audit_status": "execution_error"
}
```

LLM 从 ToolMessage（JSON 字符串）中可直接读取 `error_type`、`suggestion` 等字段，精准定位问题并调用正确工具修正。

#### 关键设计决策

- **放在工具内部而非安全护栏**：安全护栏（`safety.py`）在适配器连接之前执行，无法复用数据库连接。工具内部已有连接逻辑，错误解析不增加额外开销
- **不修改 tool_node.py**：`run_query` 的 except 现在返回结构化 dict 而非抛异常，ToolMessage 走正常 `_json.dumps(result)` 路径（第 183 行），不会被截断
- **不修改 AgentState**：纯工具层面的改动，零状态
